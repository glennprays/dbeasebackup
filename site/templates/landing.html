Self-hosted · Database backups · MIT licensed

Database backups on a schedule, checked and shipped off the box.

DBEaseBackup runs each target's backup on its own cron schedule, verifies the result, uploads it to Google Drive or S3, and deletes copies older than your retention window. PostgreSQL is supported today through pg_dump and pg_basebackup; more engines are planned.

01 / A run

What happens every time a schedule fires

The same seven steps for every target. Each one is logged with the run's trace ID.

  1. 01

    Schedule

    Each target fires on its own cron expression in SCHEDULER_TIMEZONE. A trigger that arrives while the previous run of that target is still going is skipped, not queued.

  2. 02

    Back up

    pg_dump -F c for one database, or pg_basebackup -Fp -Xs for the whole cluster, into the target's local backup_dir.

  3. 03

    Verify

    Base backups pass pg_verifybackup before anything leaves the host. Dumps are downloaded again after upload and read with pg_restore --list.

  4. 04

    Upload

    To a Google Drive folder with 8 MiB resumable chunks, or to an S3-compatible bucket under S3_PREFIX.

  5. 05

    Clean up locally

    The staging file is deleted, also when a later step fails, so the disk does not fill up.

  6. 06

    Retry and report

    A failed attempt retries after 30 s, then 2 min. When the run ends, one webhook signed with HMAC-SHA256 reports the outcome.

  7. 07

    Retention

    A cleanup job lists storage, reads the UTC timestamp in each filename and deletes files older than retention_days. No catalog database to keep in sync.

02 / Configure

One file lists every target

Each target carries its own connection, schedule, mode, retention, retries and storage folder. Secrets stay in the environment.

name
Prefix of every file and the key retention uses to find them.
password_env
Name of an env var holding the password. It reaches pg_dump as PGPASSWORD, never as an argument.
schedule
Standard five-field cron. Stagger targets to spread load.
retention_days
0 keeps everything; the default is 30.

04 / Storage

Off the database host, into storage you already pay for

Google Drive

A service account uploads into a folder you share with it, one folder per target.

  • Resumable uploads in 8 MiB chunks, flat memory use
  • storage.folder_id per target
  • Health check lists one file to prove the key works
{{template "link-more" (dict "Href" "/docs/google-drive/" "Label" "Set up Google Drive")}}

S3 and compatible

AWS S3, MinIO, Cloudflare R2, Backblaze B2 or DigitalOcean Spaces through one client.

  • Keys at <S3_PREFIX>/<filename>
  • Needs only ListBucket, PutObject, GetObject, DeleteObject
  • Health check confirms the bucket exists

05 / Operate

Easy to watch from the outside

Probes for your orchestrator, a webhook for your alerts and JSON logs for your collector.

GET /health
200 while storage is reachable, with each target's last run, last success and last error.
GET /readyz
Readiness probe; turns false as shutdown begins.
GET /livez
Liveness probe; the process answers.
X-Signature-256
HMAC-SHA256 of the webhook body, keyed with WEBHOOK_SECRET.
